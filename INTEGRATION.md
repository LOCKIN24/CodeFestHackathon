# Adding a microservice later

No new service was implemented. Official bridge documentation is linked from https://tpe-guideline.web.app/en/docs/ under Two-Way Connection. Validate the current API and challenge rules when development begins.

1. Add the Vue view/components and a route in `TownPass-Services/src/router/index.ts`; use Pinia stores only where shared state is needed. Set a route title and ensure the production host serves the SPA entry point for direct deep links. Test direct navigation and back navigation.
2. To expose it in the existing service catalog, add an enum case and its `MyServiceItem` in `TownPass/lib/page/city_service/model/my_service_model.dart`, including title, icon, category and destination URL. Existing pinned/trending widgets call `TPRoute.openUri`; `local://` routes to a GetX route, while other URLs open `TPWebView`. Other hard-coded links live in individual Flutter views. Regenerate assets if adding an asset. Test the catalog and editing/pinning behavior.
3. Deploy the web application to a reachable HTTPS origin, or for development point a temporary local-only catalog URL at the server. For simulator local testing, loopback may be used subject to iOS transport policy; for a phone, bind Vite to the Mac's LAN interface, use the Mac's LAN address, and test network/firewall and iOS transport restrictions. A local HTTP exception, if necessary, must be narrowly scoped and removed before release. Do not assume the existing production URLs change automatically. These local-WebView paths were not verified here.
4. For an existing bridge operation, register `useHandleConnectionData` before sending with `useConnectionMessage(name, data)`, parse `event.data` and match `name`. Check each handler's actual reply behavior. For a genuinely new capability, agree a versioned request/reply schema and implement a handler in `lib/util/web_message_handler/tp_web_message_handler.dart` and register it in `tp_web_message_listener.dart`. Restrict trusted origins and main frame, validate input, avoid sending private data without a clear need, handle denial and errors, and test both platforms. The current default listener has no explicit origin restriction in this project.
5. Test in a browser, then inside the simulator WebView and on a physical device. Browser-only rendering does not exercise `flutterObject`; a device may need signing and permission prompts. Verify dependencies and backend behavior independently; much sample content is mock data.
