# Proposed navigation boundary — not implemented

Use a reviewed, versioned mapping from feature ID to a typed destination and parameter schema. A future service should expose a preview of the destination and a separate open operation requiring explicit user confirmation. It should reject unknown IDs, unvalidated parameters, stale confirmation, missing prerequisites and destinations outside its allowlist. The app, not the model, selects the GetX route, tab index or fixed HTTPS origin/path. Never expose arbitrary URLs, JavaScript, bridge messages, OS actions or form submission to the model. Recheck application state immediately before navigation; return structured success, denial and failure, and do not assume page load means successful completion.

The current `TPRoute.openUri` accepts non-local URLs, so it is not itself an appropriate AI boundary. `TPWebMessageListener` receives sourceOrigin and isMainFrame but the dispatcher does not validate them. Existing `flutterObject` handlers include location, user info, phone calls, link opening, notifications and QR scanning: review origins, frames and payloads before exposing any privileged operation. See `TownPass/lib/util/web_message_handler/` and `TownPass-Services/src/composables/`. No implementation or security audit is complete.
